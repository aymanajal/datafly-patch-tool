# 日常使用

## 更新后端

1. 确认处于预定维护窗口，登录正确的测试或正式环境。
2. 选择本地后端 JAR。文件名不限，例如 `1.jar`。
3. 点击“上传并校验”，核对文件名、大小、时间和 SHA-256。
4. 点击“执行更新”，核实服务器及目录，输入“更新影像”确认。
5. 等待任务结束。工具依次校验、暂存、备份、停止、替换、启动、检查。
6. 检查通过后访问影像功能，确认业务可用。

上传文件使用内部唯一编号保存。只有执行更新后才替换正式 `datafly-admin.jar`。文件内容仍必须是兼容当前应用的正确补丁，JAR 校验不能代替版本检查。

停止脚本超时默认为 120 秒，启动检查最多等待 300 秒，进程与端口需要连续稳定 10 秒。不会强杀 Java。失败停止后续步骤，先看任务记录和实际状态，不要重复提交。

## 回退

在“备份与回退”选择目标版本。回退流程同样会暂停服务，并先备份当前版本。回退后检查业务功能。备份不是版本标签，必要时根据任务时间和摘要核实对应补丁。

## 存储

- 上传文件：配置 `data_dir` 下的 `uploads/`，页面可删除不再需要的文件。
- 任务与脚本输出：`data_dir/jobs/`。
- 旧包备份：业务部署目录中的 `patch-backups/`。
- 上传默认单文件最多 1GB，累计最多 5GB；旧包备份不自动清理。

确认容量后定期人工归档备份。不要把以上运行文件上传 GitHub。

## 工具服务管理

```bash
systemctl status datafly-patch-web --no-pager
journalctl -u datafly-patch-web -n 100 --no-pager
```

只有确认没有更新任务后，才重启工具：

```bash
systemctl restart datafly-patch-web
```

配置修改后重启工具才生效。工具会话保存在内存中，重启后需重新登录。网页关闭不取消更新。工具意外退出后，未完成记录会标记监控中断，此时先核实当前包、Java 和端口，再决定下一步。

修改密码时，在无任务期间停止工具，备份并移走原配置，再执行 `--init`；保留并恢复原环境路径、端口、来源 IP 等设置，再启动。不要把初始化默认配置误用于正式业务环境。

## 命令行备用工具

```bash
DATAFLY_DIR=/实际部署目录 bash datafly-update.sh
```

命令行版保留人工确认服务停止，依赖 `unzip`、`flock` 和 GNU coreutils；网页版使用 Python 标准库处理这些环节。二者使用相同部署锁，但都不能阻止其他人手工替换 JAR，维护时仍需协调。

## 更新前端

在前端服务器的工具页面操作，确认页面标题为“前端补丁”。上传包含 dist/ 的 ZIP、校验后确认更新。完成后强制刷新影像网页并验证功能。前端模式不停止 Nginx 或 Java，详情见 [前端工具说明](FRONTEND.md)。
