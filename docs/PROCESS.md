# 从手工更新到网页工具

记录日期：2026-10-20。公开版本使用环境角色代替现场内网地址；完整现场地址保存在本地忽略文件 `PRIVATE_DEPLOYMENT.md`。

## 为什么做

原来的后端补丁更新需要先通过堡垒机登录服务器，进入部署目录，手动重命名旧 JAR、把新 JAR 改名或从临时目录复制，再依次执行 stop、status、start。每次都要重复输入命令，步骤繁琐，也容易混用两个新包来源。

希望把更新变成：选择本地文件、上传、确认、看进度。文件名可以是 `1.jar`，部署时统一变成正式包名，备份和回退也由工具管理。

## 方案如何演进

1. **命令行版**：生成服务器本机交互脚本，提供校验、带时间备份、更新和回退。因不了解实际启停脚本，最初保留人工确认服务已停止。
2. **网页版**：用户希望浏览器操作。确定采用服务器本机的独立 Python 服务，不在网页保存 SSH 密码。经堡垒机安装工具后，日常更新可通过网页完成。
3. **曾考虑 Nginx**：检查现有代理，发现网页与后端已有独立转发规则。代理方案可行，但并非必需，因此模板保留为可选。
4. **先测试**：测试环境没有 Nginx，采用浏览器直连独立工具端口。测试环境和正式环境的部署目录、后端端口不同，改为分别配置。
5. **正式落地**：正式环境同样能直连独立端口，最终未修改 Nginx。确认网页访问后改成 systemd 后台服务。

## 现场问题与处理

| 现象 | 核实结果 | 处理 |
| --- | --- | --- |
| tar 提示文件时间在未来 | 包内时间晚于服务器当时的时间，文件已解压 | 继续检查解压文件，没有把警告当成解压失败；本次未调整服务器时间 |
| 正式 JAR 不存在或为符号链接 | 测试环境路径与最初假设不同 | 修改测试环境 `app_dir`，不移动业务文件 |
| Java PID 存在，但端口检查失败 | 测试环境实际后端端口不同 | 用 `ss -lntp` 核实对应 PID 的监听端口，再改 `app_port` |
| 页面提示来源地址不允许 | 网页已能到达工具，自身 IP 白名单拦截 | 配置运维电脑实际来源 IP；未因此关闭系统防火墙 |
| 页面提示路径不正确 | 再使用完整的末尾带 `/` 的路径后可访问 | 保持 URL 与 `base_path` 一致 |
| `-jar -D...` 预检查被拦截 | 用户提供的脚本含该写法 | 备份并调整磁盘脚本中的参数顺序，没有因此重启运行中的 Java |
| 正式端口连通，但 `pids` 为空 | 实际 Java 工作目录正确，旧进程命令行仍含 `-jar -D... JAR`；工具把紧跟的 `-D` 当成文件路径 | 修正进程识别，跳过此位置的 `-D` 属性，继续匹配实际 JAR 路径；增加回归测试 |
| 关闭 SSH 终端会影响前台工具 | 工具当时以前台方式运行 | 先退出前台工具，再安装并启用 systemd 服务 |

进程识别问题属于工具实现对现场参数的兼容不足，不是影像进程不存在。修改磁盘脚本也不会改写已经运行的进程命令行。

## 为什么不能只看 start 或 status

现场 `datafly.sh start` 在提交后台 Java 启动后就打印成功；这不能证明应用启动完成。`status` 只打印文本，不能仅靠返回码判断运行状态。脚本中的 `LOG_PATH` 也没有实际用于 Java 输出，原命令将启动输出丢到 `/dev/null`。

工具因此检查目标 Java 进程、配置的后端端口，以及连续稳定时间。它显示的是“进程与端口检查通过”，仍需人工访问影像功能确认业务可用。脚本输出与完整 Java 启动日志不是一回事。

## 验证结果和边界

- 本地最初完成 10 项隔离测试，随后为旧进程参数兼容增加回归测试，累计 11 项。
- 用户明确反馈测试环境验证通过，但没有逐项提供更新后业务检查及回退演练证据，不扩写为所有场景都已现场验证。
- 正式环境确认后端 PID 和端口均识别正确，用户确认网页可打开。
- 正式 systemd 输出显示 `active (running)`、`enabled`，Python 进程监听独立工具端口。
- 测试环境按同样步骤切后台服务，用户回复“ok”，没有单独贴服务状态；不把它写成已独立核实。
- 未在本次会话中确认正式补丁更新已执行。部署工具不等于正式版本已经更新。

## 本次公开整理的改进

源码不再固化现场 IP；新初始化默认只监听本机。页面确认框读取当前环境配置，停止日志显示实际后端端口，避免测试环境显示正式地址或错误端口。已有服务器的配置不会因此自动改变，本次本地文档和源码整理未推送到现场服务器。

## 前端流程补齐

用户随后提供 dist.zip 和旧操作截图。根据已有 Nginx root 确认静态目录后，先校验 ZIP，解压到独立暂存目录，备份旧 dist，再切换新目录。用户确认正式前端补丁生效，保留旧目录备份。没有重启 Nginx 或后端。

随后新增网页前端模式，复用现有登录、上传、日志和互斥机制，并增加 ZIP 路径检查、失败恢复与目录回退。采用前端服务器本机执行，避免从后端工具跨机器写入。前端工具目前尚未现场部署；本地增加 11 项前端测试，总计 22 项。
